# The BI workload: LDBC SNB Business Intelligence reads as plans on the LDBC stores

A sibling of `ldbc/` and `microbench/`: the same schema and stores, its own queries, plans and params; nothing under
`ldbc/` imports it.

**Data:** the Interactive v1 graph, not LDBC's BI dataset (another generator, with other friendships, activity and
dates), so both workloads read the same stored graph. The difference is described in the source repository's `ldbc-snb/README.md`, "LDBC's BI dataset vs ours" (tag artifact-freeze-20261026).

**What it is.** The read queries of LDBC SNB BI (spec v2.2.4, chapter 8) written as physical plans in the plan IR,
run by the C++ evaluator on every format's store, so a whole-graph analytical workload can be priced in KV ops
and bytes beside the Interactive suite. The reference Cypher (`github.com/ldbc/ldbc_snb_bi`, `neo4j/queries/`)
settles each query's reading; the per-query module cites it and names what it fixed.

**Scope today:** 17 of the 20 BI reads. On the five engine formats: BI1, BI12, BI9 (whole-graph scans),
BI2, BI5, BI7, BI8 (tag-anchored), BI3 (class + country). On Dgraph and NebulaGraph only (the registry's "batch2"
group): BI14, BI11, BI6, BI4, BI13, BI18, BI16 (+ its index twin `bi16_index`), BI17, BI10. Out of scope: BI15,
BI19, BI20 (weighted shortest paths).

## Run

```
# params (committed under inputs/params/ldbc/sf<SF>/bi/; regenerated byte-identically when missing)
$PYTHON -m kvevaluator.workloads.bi.genparams --sf 0.1
# the plan IR (committed under plans/; the drift guard compares)
$PYTHON python/kvevaluator/plan_choice/dump_planir.py --family bi
# counts on the C++ evaluator, the named formats' stores: every body of every query (the scan twins as candidates of
# their base), one file per store under output/captures/ldbc/sf<SF>/bi/reported/{counts,steps}/<store>.csv,
# reused when fresh (the nine cells: experiments/meta/run-bi-cells.sh)
$PYTHON -m kvevaluator.measure.grid_bodies --sf 0.1 --family bi --format dgraph,nebula,arangodb,pertype_csr
# correctness: C++ vs the Python oracle (counts + rows), and the independent CSV computation
#   the standing gate (`just cpp-diff`) runs every BI plan file on nebula and dgraph with 2 params
#   (~1 min per format); before a merge run the full form: 5 params, arangodb too, and pertype_csr (~1.5 h: its
#   Python twin's chase) -- pertype_csr's and arangodb's BI rows carry the format-level label-from-id finding, so a
#   mismatch there is read against the results doc's "Which numbers stand" first
for f in nebula dgraph arangodb; do
  $PYTHON tests/gates/check_cpp_vs_python.py --sf 0.1 --families bi --format $f --store $f --pack --skip-bytes; done
$PYTHON tests/gates/check_cpp_vs_python.py --sf 0.1 --families bi --pack          # pertype_csr-c64k, the default
```

## Files

| file | what |
|---|---|
| `queries/bi<N>.py` | one query = one builder (a parameterized `Plan`); `SIM = {name: builder or {"default", "<format>"}}` |
| `queries/__init__.py` | `REGISTRY`, `GROUPS` / `QUERIES`, `plan_for` (binds + lowers the logical type filter per format) |
| `_shared.py` | BI's constants and the one shared helper (`message_prop_steps`: the messages among a Tag's hasTag-in list) |
| `params.py`, `genparams.py` | the factor-based parameter families (spec 8.3's idea on our data); `SLICE_PARAMS` = (typical, heavy) per query |
| `plans/` | the dumped IR, one file per query (a capability bundle where dgraph's body differs) |

## What the plans charge, and the choices that are ours

- **Entry to a date-bounded scan** (BI1, BI12, BI9): the sorted creationDate index of the message labels
  (`read_index_range`), exact on the value-sorted indexes, a day-granular superset on dgraph's token index that a
  filter trims. dgraph's index is also per PREDICATE, not per label: Persons and Forums fall in the window, so
  dgraph's body restricts it by the type postings (two posting intersections). The type-pass alternative
  (enumerate the labels, read the date with the props) is the planned second candidate body for the chunked
  layouts; not built yet.
- **The type of a message** (Post or Comment) in a date window: three bodies, by what the layout offers
  (`_shared.message_window_steps`; the dumper emits them as one capability bundle per query):
  the **label-scoped** body (nebula, arangodb, the per-type layouts: a props read under the Post label
  misses on a Comment, so the hits are the Posts and the rest read under the Comment label -- one read per
  message, no type probe), the **posting** body (dgraph: a uid carries no type and its date index is per
  predicate, so the two type postings restrict the window first), and the generic **probe** body (the fallback).
  What each costs, BI1 at sf0.1 p2 (143,372 messages before the date; `kvbench --backend cpp`):

  | format | S | G | N | bytes | what the ops are |
  |---|---|---|---|---|---|
  | dgraph (posting) | 3 | 286,790 | 672 | 8.4 MB | the day-token walk (672 NEXT), 2 type postings (~4.6 MB of uids), 2 prop GETs per message |
  | nebula (scoped) | 2 | 223,411 | 143,372 | 20.0 MB | the index walk (1 NEXT per entry), 1 Post-label GET per message (80,039 miss) + 1 Comment-label GET per miss; the probe body cost 366,783 G |
  | arangodb (scoped) | 2 | 510,155 | 143,372 | 43.5 MB | as nebula, with a doc read = pk + doc (2 GETs) |
  | dgneb (scoped; retired) | 2 | 223,449 | 1,297 | 17.2 MB | its per-type day index (1 SEEK per day bucket), then as nebula |
  | pertype_csr (scoped) | ~450 chunk SEEKs | 0 | 143,372 | 14 MB of chunks | the index walk, then whole 64 KB chunks (one landing serves many rows) |

  The **scan twins** (`bi1_scan`, `bi12_scan`: enumerate both labels by the type index, read the date with the
  props, filter) are measured beside the base: at p2 nebula pays 286,744 G + 286,744 N (every message) against the
  index body's 223,411 G + 143,372 N; at p5 (every message) the two meet. The pick rule (ops + bytes/4096) chooses
  per format from this fixed candidate set.
- **Content present** = `length > 0`: on the LDBC data a Post has content or an imageFile (then length 0), and
  every Comment has content; the CSV check tests `content` itself (`_shared.py`).
- **A Tag's hasTag-in list holds Forums** (hasTag runs from Post, Comment and Forum), and a vid is opaque at query
  time (`vids.py`: a format never parses a vid for its type), so `message_vids_steps` / `message_prop_steps` lose the
  Forums by a storage fact: dgraph's type postings; the no-test plan whose message-only reads miss on a Forum (BI5,
  BI7, BI3 elsewhere); the labelled props read's null row (BI2, BI8 on nebula, pertype_csr); a per-vid probe
  asked by the plan (BI2, BI8 on arangodb). The first version used the vid's group tag (`vid_tag`, 0 KV) on the
  non-dgraph formats; the sf0.3 deltas are in the results doc ("Which numbers stand"); the sf3
  rows were re-measured (the snapshot `output/sf3/kvstats/bi-20261008`). Two formats resolve a label from the vid INSIDE their code (pertype_csr's
  `labels_for`, arangodb's `coll_of`): a separate, repo-wide finding, in the same doc section.
- **hasInterest has no reverse adjacency in the schema** (`reverse: false`): BI8's "persons interested in $tag" is a
  Person scan with each person's interest list read -- the plan the declared schema allows, charged to every
  format alike.
- **Everything after the reads is 0-KV flow** (group_agg, left_join, joins, sorts): BI's aggregation CPU is not in
  KVCost by construction; the latency proxy work says how much of a plan wall that is.

## Large runs: the server under numactl, with a memory ceiling

A level-wise chase at sf3 materializes millions of rows per level and the executor keeps every step's output until
the plan ends; on a machine with 4 NUMA nodes × ~48 GB a single-node server was OOM-killed at 50.8 GB while the machine had
100+ GB free. Run the C++ server through `cpp/kvevaluator/run-interleaved.sh` (`KVEVAL_CPP_BIN=<it>`: `numactl
--interleave=all` plus `ulimit -v`, 120 GB by default, so the process fails on its own rather than the kernel picking
a victim — another job runs on the same machine):

```
KVEVAL_CPP_BIN=$PWD/cpp/kvevaluator/run-interleaved.sh $PYTHON -m kvevaluator.measure.grid_bodies --sf 3 --family bi --format <one format>
```

**The rule at sf3 and above: one format at a time** (grid_bodies opens one server at a time; the record below is of the
counts driver before it, kvbench, retired, run one query per invocation; the retired driver `run-bi-counts-serial.sh` (not shipped)
did it: `QUERIES=... FORMATS=... PARAMS=...`, started only when the machine has
`MIN_AVAIL_GB` (110) available, waiting at most `WAIT_MAX_MIN` (60) for it). kvbench keeps one server per format
open for the whole invocation and each retains its peak; five level-wise servers at sf3 once summed to the whole
machine's memory. The per-process ceiling bounds one server, not the sum. One
query per invocation because the kvstats upsert replaces a query's rows per invocation: a run with all of the query's
params leaves no ghost cell (a `--param p` slice would drop the other params' rows of record). **Two stop rules**,
checked after every query, exit 9 with the query and the value: `STOP_RSS_GB` (40) on the peak RSS of this run's
own server, `STOP_ROWS` (3,000,000) on the largest `rows` of the query's steps in the steps file of record. A known
heavy cell runs on its own with the knob raised for that query alone (BI runs on
the nine cells, `experiments/meta/run-bi-cells.sh`; the lines below are its record), e.g.
`QUERIES=bi17 FORMATS=dgraph,nebula STOP_RSS_GB=48 STOP_ROWS=20000000` (sf3 BI17 p5
peaked at 41 GB with a 16.7 M-row join; BI6 p5 has a 7.6 M-row step). Smoke-tested at sf0.1 (`STOP_ROWS=1000` stops
on BI1's 302,022-row window step; the defaults run BI1 + BI12 through, 6 s + 11 s, peaks 0.5 / 0.9 GB).
